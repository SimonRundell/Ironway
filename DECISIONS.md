| 2026-10-16 | T1.01 | `cargo.json`'s category enum includes `special` (for `ships`) in addition to the five categories DESIGN 6.2 names | Appendix A lists `ships` as category `special`, which 6.2's prose list omits. Appendix A is the literal starter data, so the validated enum follows it rather than silently reclassifying ships as `general`. |
| 2026-10-16 | T1.01 | `industries.json` inputs are a list of requirements, each either `{cargo, qty}` (AND) or `{any: {cargo: qty, ...}}` (pick one) | Needed to represent Appendix B's "flour 400 or livestock 200 or milk 300 or fish 100" (Food works) and the mixed "iron 200 or steel 200, coal 60" (Engineering works) faithfully. A flat cargo-to-qty map can't express the "or" groups. |
| 2026-10-16 | T1.01 | Numbers Appendix A-F don't actually specify (farm yields per cell, vehicle reliability/gradeFactor, industry maxPerNode/storageMonths, difficulty presets, rank thresholds, mapgen noise frequencies, world trade caps) are invented starter placeholders | DESIGN 11 says explicitly "All numbers in the JSON files... are starter values. Expect a tuning pass." Picked round, internally consistent numbers rather than stalling on precision that T1.25's balance harness will retune anyway. |
| 2026-10-16 | T1.01 | Generation thresholds (`mountainLine`, `rockSlope`, moor/marsh bounds, `lakeDepth`) live in `mapgen.json`, not `terrain.json` | DESIGN 8.1 splits "all generator parameters" (mapgen.json) from "land use enum, colours for Phase 1 debug view, thresholds" (terrain.json) without saying which file owns classification thresholds used *during* generation. Keeping them with the generation pipeline avoids two sources of truth for the same numbers; terrain.json is left holding only the enum and debug colours. |
| 2026-10-16 | T1.01 | react-doctor's "fetch Response consumed without status check" at `src/sim/rules.js` `loadRulesBrowser` is a reviewed false positive, left as-is | The code does check `response.ok` and call `fail()` (which always throws `RulesError`) before `response.json()` runs. The linter doesn't trace into the `fail()` helper to see it never returns, so it can't see the check already guards the call. |
| 2026-10-16 | T1.02 | Noise is seeded *value* noise (lattice hash + Perlin's quintic fade polynomial), not gradient/simplex | DESIGN 5.2 step 2 literally asks for "fBm value... noise", and value noise needs only integer hashing and polynomial interpolation, with no gradient-angle maths at all — simpler and a sure fit for the "no Math.sin, no fractional Math.pow" rule in DESIGN 4.5. |
| 2026-10-16 | T1.02 | `gaussian()` in rng.js uses the Irwin-Hall (sum-of-12-uniforms) approximation instead of Box-Muller or the Marsaglia polar method | Both of those need `Math.log` and/or `Math.sin`/`Math.cos`, which DESIGN 4.5 doesn't whitelist for generator/simulation maths (only `+ - * /`, `Math.floor`, `Math.sqrt` and integer hashing are). Summing uniforms is exact-arithmetic-only and good enough for game generation, at the cost of slightly thinner tails than a true normal. |
| 2026-10-16 | T1.02 | `checksum()` uses 64-bit FNV-1a via BigInt, formatted as 16 lowercase hex characters | Matches `save_map.checksum CHAR(16)` in `api/sql/001_schema.sql` exactly, and BigInt arithmetic is exact (no floating-point rounding), keeping the hash itself cross-engine deterministic. |
| 2026-10-16 | T1.02 | The `Math.random` grep guard (`src/sim/noRandom.test.js`) searches for the call form built via string concatenation, not the literal text | A literal `'Math.random'` (or worse, `'Math.random('`) written directly in the guard's own source would make the guard fail itself, since it legitimately has to mention what it is checking for. Searching for the call form (with the open paren) also avoids false positives on prose mentions like "no Math.random anywhere" in other files' comments. |
| 2026-10-16 | T1.03 | The mountain ridge's "weighted by a Gaussian of distance to the nearest spine" (DESIGN 5.2 step 3) is a polynomial bump `(1 - d^2)^2`, not a literal Gaussian | `Math.exp` isn't in DESIGN 4.5's exact-arithmetic whitelist and can differ in its last bit between JS engines; a bump function gives the same qualitative smooth falloff to zero using only `+ - *`. |
| 2026-10-16 | T1.03 | Mountain spines walk in one of 8 discrete compass directions rather than a continuous angle | Turning via an angle would need `Math.sin`/`Math.cos` to convert to a step; a small fixed direction table avoids trig entirely and is indistinguishable at this grid resolution. |
| 2026-10-16 | T1.03 | Final land/sea elevation (metres) is scaled against the 98th/2nd percentile of the land/sea height distributions, not the literal min/max, and clamped to the output range | Scaling against the literal max let a single lucky noise spike stretch the whole land range and drag an otherwise-substantial mountain mass below the 900m rock line — 17 of 20 seeds failed the "40+ rock cells" check with max-based scaling, 0 of 20 fail with percentile-based scaling. |
| 2026-10-16 | T1.03 | Erosion's steepest-descent neighbour search only ever considers land neighbours (`water === 0`) as a transfer target | Without this restriction, a coastal land cell could have a sea cell as its lowest neighbour and erosion would move material into it, pushing some sea cells' `elev` positive over enough passes — breaking the invariant that `elev` sign always matches `water` classification (caught by a 20-seed regression test added alongside the fix; manifested visibly as literal `"undefined"` text in the ASCII debug preview, from an out-of-range ramp-array index). |
| 2026-10-16 | T1.03 | Erosion uses a high talus angle (15m) and small transfer fractions (thermal 0.1, stream-power 0.02) per pass | The first attempt (talus 2m, transfer 0.5) was aggressive enough that 20-40 passes eroded freshly-built 1300m peaks down to 500-700m, failing the rock-line test even though the pre-erosion terrain had plenty of qualifying cells. DESIGN 5.2 step 5 calls this "light" erosion. |
| 2026-10-16 | T1.04 | `mapgen.json` soil thresholds renamed from `rockSlopeDegrees`/`marshMaxSlopeDegrees` to `rockSlopeRatio`/`marshMaxSlopeRatio` (precomputed tan(25°)=0.4663, tan(2°)=0.0349) | T1.04's slope layer stores a quantised rise/run gradient ratio, not an angle (converting a ratio to degrees needs `Math.atan`, not in DESIGN 4.5's whitelist). These two field names were my own invention in T1.01 with no DESIGN mandate behind the "degrees" unit, so correcting them now (before anything consumes the old names) avoids ever needing trig at runtime to compare against them. |
| 2026-10-16 | T1.04 | Priority-flood depression filling and D8 flow direction are computed in one combined pass, not two separate ones | When a cell is popped from the fill priority queue (in increasing filled-elevation order) and relaxes a neighbour, that neighbour's downstream flow direction is, by construction, back towards the popping cell. Recording this at fill time gives a flow-direction tree that is cycle-free and rooted at the sea for free; computing direction afterwards by comparing neighbour elevations risks ambiguous ties on the flat surface of a filled depression (a lake). |
| 2026-10-16 | T1.04 | River width class uses an exact integer log2 (count leading-zero bit shifts) rather than `Math.log2` | `Math.log2` is a transcendental function outside DESIGN 4.5's whitelist; the width class only needs `floor(log2(n))` for a positive integer ratio, which bit-shifting computes exactly with no floating point at all. |
| 2026-10-16 | T1.04 | Flow accumulation (sum of rain over a cell's whole upstream drainage area) is kept as a working `Float64Array` and only scaled into the `flow` Uint16 layer via a fixed `flowScaleDivisor`, not a per-island normalisation | Raw accumulation for a large drainage basin can reach millions, far past Uint16's 65535 ceiling; normalising against each island's own maximum would make `riverThreshold` mean a different thing on every seed. A fixed divisor keeps the threshold's meaning consistent across seeds, at the cost of needing to tune the divisor empirically (see the T1.04 entry below). |
| 2026-10-16 | T1.04 | `mapgen.json` hydrology retuned: `lakeDepth` 3 to 50, `riverThreshold` 5000 to 200 | Both were untested T1.01 placeholders. At `lakeDepth: 3`, almost every minor noise-induced dip in the terrain exceeded it, so 350-1850+ cells (up to ~8% of land) were misclassified as lakes per island, swallowing exactly the valley-bottom cells that should have carried rivers. At `riverThreshold: 5000`, typical scaled flow (max ~2500-10000 across 20 seeds) rarely cleared it, so most islands had zero or one short river. Checked actual output across all 20 seeds at each step rather than guessing: final values give realistic lake coverage (0-4% of land) and 3-24 rivers over 100 miles per island (every seed comfortably clears the 3-river minimum), with zero uphill-flow or drains-nowhere violations. |
| 2026-10-16 | T1.05 | The 16 shelter-ray directions are derived from half-angle identities (`cos(22.5°) = sqrt(2+sqrt(2))/2`, `sin(22.5°) = sqrt(2-sqrt(2))/2`), not `Math.sin`/`Math.cos` or hardcoded decimal literals | Keeps the directions exactly derivable from `Math.sqrt` and arithmetic (DESIGN 4.5's whitelist) while staying self-documenting; a wall of 32 unexplained decimal constants would have worked too but hidden where the numbers come from. |
| 2026-10-16 | T1.05 | Extracted `clampByte` into `grid.js` as a shared export, used by climate.js, slope.js and coast.js | It was about to be copy-pasted a third time with identical logic; a shared home in the layer-container module is a natural fit since every caller is clamping a value into a Uint8 layer. |
| 2026-10-16 | T1.05 | `selectHarbourCandidates` guarantees `minEstuaryHarbours` by evicting a conflicting *non-estuary* site from the already-selected list, rather than relaxing the 40-mile spacing rule for estuaries | A first attempt that only added estuary candidates when they didn't conflict with anything already selected still failed 1/20 seeds: a dense coastline can leave every surviving river-mouth cluster within 40 miles of some higher-scoring plain-shelter site, so "only add if no conflict" never found room. DESIGN 5.3 requires both minimums (10 candidates, 3 estuaries) *and* the spacing rule simultaneously, so relaxing spacing wasn't an option; evicting the specific blocking non-estuary site preserves the spacing invariant for the final list. Never evicts another estuary. Fixed the one failing seed (ironway-010, 2 estuaries to 3) without disturbing the other 19. |
| 2026-10-17 | T1.06 | Arable/pastoral differentiation in `soil.js` scores relative elevation, not slope | The non-rock, non-moor farming band turned out almost perfectly flat on every seed (99.9% of it in the lowest slope bucket out of the rock threshold), so a slope-based split between "lowland arable" and "hilly pastoral" had nothing to differentiate on. Elevation still varies meaningfully across that band even where slope doesn't, so `elev / moorElevationMinMetres` became the upland/lowland signal instead. |
| 2026-10-17 | T1.06 | Forest placement in `soil.js` perturbs a direct threshold comparison with noise (`score + (noise - 0.5) * spread > threshold`), rather than using noise as a probability gate (`noise < score * maxProbability`) | `fbm2D` sums several octaves of value noise, which clusters its output near 0.5 (a central-limit-like averaging effect) instead of spreading uniformly over [0, 1). Comparing it against a small probability as if it were `Math.random()` almost never succeeds, since the noise rarely dips that low — an early attempt at the probability-gate form gave 0-0.5% forest on every seed despite healthy underlying forest scores. Noise is a good *spatial perturbation* on a threshold (soft, noise-shaped patch edges); it is a poor stand-in for a uniform random draw. |
| 2026-10-17 | T1.06 | `soil.js` and `resources.js` each end with a deterministic top-up step (promote the highest-scoring cells of a short class, or force a deposit onto the best remaining site) when natural generation falls short of a DESIGN minimum | Even after the elevation/rain fixes, 5 of 20 seeds (unusually low-lying, high-marsh islands) couldn't reach 5% pastoral from scoring alone, and some seeds don't naturally land 3 coal-iron pairs within 60 miles of each other. Rather than keep reweighting formulas to chase specific seeds' terrain shapes, both modules guarantee their DESIGN minimums directly: `soil.js` promotes the highest pastoral-scoring arable/mixed cells until the 5% floor is met; `resources.js` falls back to any unclaimed land cell per type if a type's siting rule can't reach its minimum count, and forces a small iron deposit near an unpaired coal deposit if short of 3 proximate pairs. Same pattern as T1.05's estuary-eviction guarantee: score-based generation first, a deterministic correction only if the guarantee isn't already met. |
| 2026-10-17 | T1.06 | `RESOURCE` enum (none, coal, iron, stone, clay) is a frozen object exported from `resources.js`, not a `terrain.json` field like `landuseEnum` | DESIGN 5.1 states the resource enum directly in the layer table with no mention of a JSON source, unlike `landuse` which DESIGN 8.1 explicitly assigns to `terrain.json`. Keeping it as a code constant next to the module that uses it (mirroring `COAST_FLAG` in `coast.js`) avoids inventing a JSON field DESIGN never asked for. |
| 2026-10-17 | T1.07 | Added `coastalEndingChance`, `prefixChance` and `maxAttempts` to `names.json` rather than hardcoding them in `names.js` | Keeps with the convention set in `mapgen.json` for the generation pipeline: tunable generator parameters live in the validated JSON rules, not as magic numbers in the module that consumes them, so a later balance pass can retune naming flavour without touching code. |
| 2026-10-17 | T1.07 | A coastal settlement's ending is drawn from `coastalEndings` with probability `coastalEndingChance` (0.75), not forced | DESIGN's "Done when" bar is "at least 60 percent" of coastal settlements showing a coastal ending, not all of them — a real coastline has plenty of settlements named after a person, a feature, or a saint rather than the sea. 0.75 clears the 60% bar with comfortable margin (measured 76-78% across two seeds) while still leaving room for inland-style names on the coast. |
| 2026-10-17 | T1.07 | `createNameGenerator`'s uniqueness and blocklist checks compare names case-insensitively, and each name category (settlement, river, bay, range, island) keeps its own draw counter rather than sharing one global counter | Case-insensitive comparison matches how a human would judge two names as "the same" (DESIGN just says "unique", and a save with both "Ashton" and "ASHTON" would read as a bug, not a feature). Per-category counters mean a settlement name's rng key depends only on prior settlement draws, not on how many rivers or bays happened to be generated in between — any change to how many rivers a future task asks for can never silently reshuffle every settlement name that follows. |
| 2026-10-17 | T1.08 | `toRows()`/`fromRows()` cover a `GameState` (settlements, industries, links, economy, company, history, events) rather than the full `World` DESIGN 4.4 describes (which also has grid, harbours, names and meta) | Those four extra `World` fields each have their own, different persistence path already implied elsewhere in DESIGN: the grid is a separately gzipped blob (5.1), harbours and names are derived from the grid rather than stored in their own SQL tables, and meta (seed, generator version, difficulty, save name) lives on the `saves` row itself, written by `saves/create.php`, not by an entity-row checkpoint. Matching DESIGN 4.4's own checkpoint wording ("changed entity rows, new history rows and new event rows") kept the round-trip contract honest: every field `toRows()` touches has one unambiguous SQL column to round-trip through. |
| 2026-10-17 | T1.08 | `gameDay` and `version` are not part of `GameState`/`toRows()`; `SimState` carries `gameDay` alongside a `GameState`, separately | Both columns live on the `saves` row, not on any entity table, and DESIGN 4.4's checkpoint body lists them separately from "changed entity rows" (`"id, baseVersion, gameDay, changed rows..."`). Folding them into `GameState` would have made `toRows()` respond to a table that `saves/checkpoint.php` updates through a different code path (`saves.php`, not the per-entity chunked upsert). |
| 2026-10-17 | T1.08 | The dirty tracker is a thin `Set` wrapper that records *which* string keys changed, not snapshots of *what* changed | Simulation code is expected to mutate `GameState`'s entities in place (DESIGN already treats `World`/`SimState` as the live, authoritative in-memory copy) and call `markDirty("settlement:3")` alongside the mutation. Since the entity itself already holds the new value, the tracker only needs to remember which keys to re-serialise at checkpoint time — storing a second copy of the changed data would be redundant bookkeeping with its own chance to drift out of sync with the real entity. |
| 2026-10-17 | T1.09 | Widened `grid.region` from Uint8Array to Uint16Array, deviating from DESIGN 5.1's literal "Uint8" | DESIGN 5.4's own settlement count ranges sum to as many as 331 settlements on one island (1 capital + up to 8 cities + 32 towns + 130 villages + 160 hamlets), and `region` stores a settlement's id — a real id above 255 would silently wrap and corrupt hinterland data on any sufficiently populous seed, which is common, not an edge case (minimum-case counts alone can exceed 255). Caught and fixed before anything wrote to the layer, the same category of fix as T1.04's slope-unit correction. |
| 2026-10-17 | T1.09 | Settlement population is "rank-size shaped" (DESIGN's own phrase) *within* each kind via a `popFractionFloor`-anchored taper, not a single Zipf/rank-size curve spanning all settlements together | A single global curve calibrated to hit both every kind's own population range and the 2-3 million total at once is fragile: a quick check of a literal 1/rank Zipf weighting matched city/town/village ranges reasonably but pushed hamlets (rank ~147-281 of ~300) past their own 1,000 maximum. Shaping within each kind sidesteps that cross-kind calibration problem entirely, while still giving the first-placed (best-scoring) settlement of a kind the top of its range and later ones progressively less, which is the actual DESIGN intent (a city's size varying with its site, not identical cities). |
| 2026-10-17 | T1.09 | `popFractionFloor` is 0.4, not 0 (a plain 0-to-1 linear taper) | Independent uniform population draws per settlement average to each kind's own midpoint, and summed across kinds at their expected counts that lands right at the 2 million floor — meaning a plain linear taper (equivalent to a uniform draw in expectation) would fail the 2-3 million "Done when" bar on roughly half of all seeds by chance alone. Flooring the taper at 0.4 (so fractions range 0.4 to 1.0 instead of 0 to 1.0) shifts the expected total well into the band; empirically, all 20 seeds landed between 2.19 and 2.72 million. |
| 2026-10-17 | T1.09 | The capital's placement candidates are filtered up front to buildable, coastal cells within `capitalHarbourRadiusMiles` (12) of a harbour-candidate or estuary cell, rather than scoring all cells and hoping the best-scoring one happens to qualify | DESIGN 5.3 treats the 12-mile capital-to-harbour distance as a hard validation rule, not an emergent one. Filtering eligibility before scoring guarantees it unconditionally (the same "guarantee by construction" pattern used for T1.06's resource minimums and T1.05's estuary count), rather than relying on the scoring weights to reliably produce a compliant result across all 20 seeds and any future reseed. |
| 2026-10-17 | T1.09 | Port tier is assigned only when a settlement's own cell carries the `HARBOUR_CANDIDATE` or `ESTUARY` coast flag — not when a harbour is merely nearby | `coast.js`'s harbour candidates are themselves coastal *land* cells (not sea cells), so "sits on a harbour candidate" is a literal, checkable condition at the settlement's exact location, matching DESIGN 5.4's "Port tier 0 to 3 if it sits on a harbour candidate or estuary" and DESIGN 5.3's "every port lies on a harbour candidate or estuary" validation rule word for word. The general (non-capital) placement score still gives partial credit for being merely coastal, so port-worthy sites are preferred without being required. |
| 2026-10-17 | T1.10 | `settlements.js`'s buildable mask now also requires a cell belong to the single largest connected landmass, excluding `island.js`'s kept islets | Discovered while building road connectivity for T1.10: a settlement placed on one of the up to 3 small islets `island.js` deliberately keeps (step 4) is cut off from the mainland by sea, so no road can ever reach it — DESIGN 5.3's "every settlement reachable from the capital by road" would be violated by construction, not by bad luck. Reusing `floodFillLandmasses` (already exported from `island.js`) to find the main component and intersecting it with the existing rock/water checks was cheaper and more certain than trying to patch road connectivity around land with no route to it. |
| 2026-10-17 | T1.10 | `island.js` now also filters *sea* components after landmass filtering: any sea component that isn't the single largest is folded back into land | The land-component filter at step 4 never checked sea connectivity, so a percentile height threshold could leave behind a tiny enclosed "sea" pocket (observed: 2 cells, at a river mouth) with no 8-connected path to the open ocean. A port built next to one would get a real-looking sea lane that `findPath` can never actually complete, breaking DESIGN 5.3's "every port reachable by sea from every other port" outright rather than by chance. Folding it back into land (not directly into `lake`) was the lower-risk fix: the elevation-scaling code immediately below already treats land and sea cells differently, so reclassifying before that point gives the cell a normal land elevation for free, and hydrology's own depression-filling (which only ever examines originally-land cells) then correctly turns it into a lake if it's a genuine low-lying hollow — exactly the right outcome, reached through existing machinery instead of a hand-rolled special case. |
| 2026-10-17 | T1.10 | Road and rail share one terrain-cost function (`roadTerrainCost`): distance plus a slope penalty, a flat river-crossing penalty and a flat marsh penalty, with `rock` and water forbidden entirely | DESIGN 5.5 only qualifies rail's terrain rule as "where terrain allows" without describing a separate cost model, and historically early railways avoided the same bogs, river crossings and steep grades as roads. Inventing a second, more detailed rail-specific cost model would be unfounded precision for a Phase 1 generator DESIGN 11 already expects to retune; reusing the road function keeps the two consistent and is easy to split later if a real difference is ever needed. |
| 2026-10-17 | T1.10 | The road/sea connectivity guarantee bridges disconnected components by real A* route cost, checked only between each pair of components' single nearest-by-straight-line candidate settlements, not every possible pair across both components | DESIGN 5.4 asks for "minimum-spanning links by path cost", not straight-line distance, but evaluating A* for every cross-component settlement pair would be unbounded on a large settlement count. Checking just the one geometrically nearest candidate pair per component pair keeps the number of A* calls bounded by the (small, in practice) number of components, while still picking a real, routable bridge rather than a straight-line guess that might cross a mountain range or a bay. |
| 2026-10-17 | T1.10 | Colliery tramways (DESIGN 5.5) are deferred to T1.11, not built in T1.10 despite PHASES.md listing them under T1.10's "Do" line | A tramway needs a real id at its mine end, and no industry entities exist yet at this point in the pipeline (T1.10 runs before T1.11 by dependency order). Inventing a placeholder entity type to reference a resource deposit instead, only to reconcile it with a real industry id once T1.11 places mines on those same deposits, would have been throwaway complexity. T1.11 already needs to place mine industries directly on resource deposit cells this module can see; adding their tramways there, with a real `industryId` to attach to, is the natural point to do it. None of T1.10's own "Done when" checks require tramway presence. |
| 2026-10-17 | T1.11 | `mapgen.json` gets a new `industries` section for placement/scoring params, rather than adding one to `industries.json` itself | `validateIndustries()` already returns the bare `industries` array (not an object), and `rules.industries.length` is relied on directly in an existing T1.01 test — changing that shape to fit a sibling `placement` key would be a breaking change for no real benefit. `links.json` already set the precedent of keeping the entity/tier catalogue and its generation parameters in two different files (`links.json` for tiers, `mapgen.json.links` for how to build the network); `industries.json`/`mapgen.json.industries` follows the same split. |
| 2026-10-17 | T1.11 | `near:<cargo>` is implemented as an always-true hard-eligibility check that only ever contributes a scoring bonus, never a candidate filter | DESIGN 5.6's own table marks it "(prefer)", explicitly distinguishing it from the other, mandatory siting rules. Brickworks' only siteRule is `near:clay`, so under this reading it can be built on any buildable, labour-served cell at all, just scored higher near a clay pit — matching a real economy where clay and coal are transportable, unlike a literal on-the-deposit requirement. |
| 2026-10-17 | T1.11 | A seed can end up with zero instances of a given primary industry (observed: iron_mine, 0 on a couple of seeds) when every qualifying deposit is more than `homeSettlementRadiusMiles` (10, DESIGN's own number) from any settlement — left as-is, not guaranteed against | Iron deposits are sited in uplands (`ironElevationMinMetres` 350-850m in `mapgen.json`), systematically farther from settlements than coal's lower, more accessible band. Confirmed by direct measurement (nearest settlement 10-48 miles away on the affected deposits) that this isn't a placement bug — a mine 46 miles from the nearest settlement genuinely has no plausible workforce under DESIGN's own rule. None of T1.11's four "Done when" criteria require every industry type to appear at least once, so adding a guarantee here would be solving a problem DESIGN didn't actually pose. |
| 2026-10-17 | T1.11 | Colliery tramway mileage is capped together with the main rail skeleton (`capCombinedRailMileage`, dropping the longest tramways first), rather than trusting T1.10's own skeleton-only cap to still hold | Found by direct measurement while wiring tramways in: one seed's combined rail total (skeleton plus tramways) came out at 15.2% of road mileage, over DESIGN 5.3's 15% ceiling, even though `generateLinks`' own skeleton-only check (T1.10) still reported well under budget in isolation — the cap was correct for what existed when it was written, but tramways added mileage on top of it afterwards. `generateIndustries` now takes the main link list as a parameter specifically to re-check the combined total, the same longest-first trim T1.10 already used for the skeleton alone. |
